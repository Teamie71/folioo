# 웹 UI 구현 가이드

구현과 리뷰를 시작할 때 [웹 Figma 기준](./design-source.md)에서 해당 화면의 PC·모바일 프레임을 찾는다. 공용 UI가 이미 있으면 실제 호출 방식과 지원 상태를 확인하고 재사용한다.

## 화면 이관

- Jira에서 유지·변경·제외 범위를 확인한다. 레거시 호출부에서 화면을 여는 진입 경로, 전환 중 유지할 화면과 상태, 다음 조작과 그 결과를 대조한다. 공유 링크처럼 URL로 직접 진입하는 흐름도 확인한다.
- 라우팅과 폴더 구조는 합의한 사용자 흐름을 충족하도록 정한다. 예를 들어 경험 맵 빠른 미리보기는 맵을 유지한 채 이전·다음 활동을 바로 확인할 수 있어야 한다. 이 흐름을 기준으로 구현과 검증 범위를 정한다.

## 공용 컴포넌트 명세 검증

기존 명세의 속성, 상태, 지원 조합은 9개 카테고리로 구성된 [Folioo 컴포넌트 문서](https://app.notion.com/p/41c1b3402b0a807f8af8f2578ae137ac)에서 확인한다.

1. **Figma**에서 대상 화면의 컴포넌트, 화면별 조합, 사용 상태를 확인한다.
2. **레거시 실제 호출부**에서 화면이 전달하는 Props, 사용자의 조작 결과, 상태를 관리하는 위치를 확인한다. 공용 컴포넌트와 기능 안에서 반복하는 조합을 함께 살핀다.
3. **레거시 Storybook이나 스토리 소스**에서 확인할 상태와 예시를 찾는다. 스토리와 실제 호출부가 다르면 차이가 나는 화면과 조건을 기록한다. 예를 들어 가입 약관은 Storybook의 단일 펼침 예시와 달리, 실제 화면에서 항목을 여러 개 독립적으로 펼친다.
4. **Figma와 실제 화면**을 다시 대조한다. 공개 Props나 지원 조합을 확정하기 전에 대표 호출 예시로 동작을 확인한다. 코드만 확인한 경우에는 브라우저에서 확인할 항목을 남긴다.

- 공용화 범위는 사용 목적, 상태 전환, 조작 결과를 기준으로 정한다. 공통 동작을 공유하는 선택 UI는 `Toggle`의 외형 조합으로 정의할 수 있고, 작업 결과를 짧게 알리는 `Toast`와 후속 조작을 제공하는 `Snackbar`는 각 사용 목적에 맞게 정의한다.
- 지원 예정, Figma 외형 확정, 코드 구현 여부를 구분해 기록한다. 예를 들어 Button의 `Focus visible`, `Pressed`, `Loading`은 상태 추가를 합의했으며 구체적인 시각 규격은 별도로 확인한다.

## 페이지 배치와 컴포넌트 스타일

| 범위                            | 기준                                                                                                                                                                        |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 페이지 배치                     | 정렬, 그리드, 반응형 배치, 화면 컨테이너 너비와 간격에 Tailwind를 사용한다. 페이지 전용 길이는 `rem`으로 지정한다. 예를 들어 헤더 영역 간격은 `gap-[1.25rem]`으로 표현한다. |
| 페이지에 표시하는 텍스트와 색상 | Figma의 텍스트 스타일과 역할에 대응하는 BUD `text` 클래스와 `vars.color`를 사용한다.                                                                                        |
| 공용 컴포넌트 내부              | 스타일과 상태는 vanilla-extract에서 관리한다. 내부 간격, 색상, 타이포그래피, 모서리, 그림자에는 명세에 대응하는 BUD 시맨틱 토큰을 사용한다.                                 |

BUD 문서의 Tailwind CSS 변수 예제는 패키지 사용법이다. Folioo 웹에서 페이지 배치와 컴포넌트 내부 스타일을 구현할 때는 위 범위를 적용한다. 필요한 토큰과 내보내기는 [BUD 토큰 사용법](../../../packages/bud/tokens/README.md)과 실제 패키지 정의에서 확인한다.

## 토큰 예외 처리

- 구현·리뷰 시 요소에 실제로 연결된 시맨틱 토큰을 확인한다. 토큰의 최종 값이 Figma 시안과 일치하는지, 토큰의 용도가 해당 요소의 역할과 일치하는지 각각 검증한다.
- 적절한 토큰이 없거나 시안과 토큰이 충돌하면 **Figma 노드·원본 값·사용 역할·영향받는 화면**을 관련 Jira나 팀의 토큰 미대응 기록에 남긴다. 실제 패키지 정의에서 토큰 유무를 확인한다. 예를 들어 `spacing['3xl']`은 이미 정의된 키를 코드에서 읽는 표기다. 이번 작업에서 적용할 예외와 공용 토큰 변경은 적용 범위가 드러나도록 기록한다. BUD 토큰 추가나 변경이 확정되면 [토큰 업데이트 절차](../../../packages/bud/tokens/README.md#토큰-업데이트-방법)에 따라 원본을 갱신한다.

## 아이콘

- 색을 호출부에서 지정하는 단색 아이콘은 SVG 원본의 필요한 `fill`·`stroke`에 `currentColor`를 사용하고 `Icon`의 `color`에 역할에 맞는 BUD 토큰을 전달한다.
- `fill="none"`과 브랜드 로고의 고정 색상은 시안과 일치하도록 유지한다. `viewBox`와 내부 여백이 있으므로 아이콘 컨테이너 크기와 실제 도형이 차지하는 영역을 함께 확인한다.
- 원본 변경, TSX 재생성, 생성물 반영은 [웹 README의 아이콘 관리](../README.md#아이콘-관리)를 따른다.

## 브라우저 검증

1. 확인할 커밋과 실행 화면을 일치시킨다. 로컬에서는 체크아웃한 커밋이 리뷰 대상인지 확인하고, 프리뷰를 사용하면 어떤 커밋의 배포인지 확인한다.
2. Figma의 해당 프레임과 구현을 대응하는 화면 너비에서 비교한다. 페이지 진입, 버튼 동작, 가로 넘침을 확인하고 타입·색상·간격 차이가 있으면 브라우저의 실제 적용값을 확인한다. 마케팅 조항처럼 Figma와 `font-weight`가 각각 `700`·`400`으로 일치해도 화면이 다를 때는 로드된 폰트, 확대 배율, 폰트 스무딩 설정까지 확인한다. [마케팅 조항 텍스트](https://www.figma.com/design/l3NWpGaPsOj5KYgt9b5hxN/?node-id=5673-11192)
3. 검증 결과에 커밋 또는 프리뷰, 환경과 화면 너비, 재현 순서, 캡처나 영상, 확인하지 못한 범위를 남긴다. 정책 페이지는 [예외 시안](./design-source.md#정책-페이지-예외)의 해당 프레임을 연결하고, 합의된 토큰 예외가 있으면 적용 이유를 적는다.
